# Capability and Collaboration Contract

Use this reference when starting a new workstream, when the user asks the agent to help produce a deliverable, or when the current division of work is causing friction.

## Separate the signals

Never infer desired assistance from skill level alone. Calibrate five independent signals for each material workstream:

1. **Capability**: what the user can currently do.
2. **Evidence**: what supports that assessment—portfolio, prior outcome, work sample, or informed self-report.
3. **Ownership**: what the user wants to author, control, or decide personally.
4. **Capacity**: what the user has time and energy to do in this phase.
5. **Objective**: learn the skill, ship quickly, preserve a personal style, or use a hybrid.

A capable user may delegate because time is scarce. A beginner may retain ownership because learning matters. Do not collapse either person into a global label such as “beginner” or “expert.”

## Capability scale

Use a lightweight scale only where it changes the plan:

- `0 — unfamiliar`: cannot yet evaluate the work reliably.
- `1 — can review`: recognizes useful versus poor output with guidance.
- `2 — can execute with support`: can produce the work with examples, critique, or tooling help.
- `3 — can lead`: can set standards and execute independently.

Prefer existing evidence. Request a small work sample only when uncertainty would materially change ownership, quality control, or risk. Do not turn calibration into an exam.

## Assistance modes

Assign a mode per workstream, not once for the whole user:

| Mode | Agent responsibility | User responsibility |
| --- | --- | --- |
| `coach` | Ask, teach, challenge, and critique | Decide and execute |
| `assist` | Supply research, briefs, raw material, checklists, or options | Create the deliverable |
| `co-create` | Produce drafts and alternatives iteratively | Direct, select, and edit |
| `execute` | Produce the agreed deliverable inside the workspace | Approve defined checkpoints |
| `operate` | Run an already-approved repeatable procedure | Monitor exceptions and approve external actions |

Default to `co-create` when the desired mode is unclear and a small reversible draft can clarify it. Never use `operate` for a new or poorly understood process.

## Minimum contract

Record only workstreams relevant to the active experiment:

| Workstream | Capability + evidence | Objective | Mode | Owner | Approval gate |
| --- | --- | --- | --- | --- | --- |
| Example: campaign concept | 3; prior campaigns | preserve authorship | coach | user | final concept |
| Example: copywriting | 1; self-report | ship quickly | execute | agent | first three captions |
| Example: design production | 2; portfolio sample | hybrid | co-create | shared | first visual system |

Also record non-delegable decisions, style constraints, privacy limits, budget, and tool restrictions.

## Calibration sequence

1. Ask one compact batch only for missing information.
2. Reflect the proposed ownership map in plain language.
3. Ask for correction when a consequential assumption remains.
4. Produce the smallest representative proof of concept.
5. Recalibrate after the user sees real output.

Treat the contract as living state. Assistance may change by phase: co-create the first product, execute approved variants, then coach the user on the next product if learning becomes the goal.

## Autonomy rules

- User-owned work must not be silently delegated to a tool or subagent.
- Agent-owned work still follows privacy, cost, tool, and external-action gates.
- Preserve the user's voice and authorship; do not erase intentional style in the name of optimization.
- Explain reusable decision rules when the user's objective includes learning.
- If the output fails the agreed standard, revise the mode, checkpoint, or tool instead of blaming the user.
